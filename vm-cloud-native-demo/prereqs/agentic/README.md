# Agent prerequisites for the existing Rocket Ramen demo

This infrastructure adds AI assistance to the presenter workspace. It does not change the application, presentation commands, traffic, database migration or reset. The proposed presentation flow below has not replaced the existing runbook.

## Findings on the demo cluster

Verified on 2026-11-07, OpenShift 4.22.20:

- OpenShift Lightspeed Operator 2.0.0 is installed. `OLSConfig/cluster` selects provider `Azure`, model/deployment `gpt-4`, at `https://llm-gpt4-lightspeed.cognitiveservices.azure.com/`. A direct authenticated request identified the deployed model as `gpt-4o-2024-11-20`.
- Authentication uses Microsoft Entra client credentials in `openshift-lightspeed/azure-api-keys`, not an OpenAI API key. Credential values must remain outside Git and terminal output.
- `spec.ols.introspectionEnabled: true` already deploys the built-in `openshift-mcp-server`. The generated service configuration connects to `https://openshift-mcp-server.openshift-lightspeed.svc:8443/mcp` with the requesting user's Kubernetes token.
- The shipped MCP configuration enables core, config, Helm, metrics, traces, KubeVirt and network-observability toolsets. It denies Secret and RBAC resources. Those restrictions are retained.
- A read-only request through the Lightspeed API called `resources_list` for VirtualMachines and VirtualMachineInstances and returned all five demo VMs. This verified the configured LLM and the console backend's live cluster integration.
- The operator reports that its newer agentic console plugin and alerts adapter require OpenShift 5.0 or newer. On 4.22, use the existing Lightspeed console panel. Do not bypass this version check. Console write-approval interactions still need presenter rehearsal; the read-only backend path was tested.

Red Hat documents the built-in integration under [How OpenShift Lightspeed accesses live cluster state and operation approvals](https://docs.redhat.com/en/documentation/red_hat_openshift_lightspeed/1.0/html/configure/ols-configuring-openshift-lightspeed). The current public documentation is served under the `1.0` documentation URL, so the installed 2.0 CRD and generated configuration were also checked rather than copying an older custom-MCP example. No duplicate MCP server entry or legacy feature gate is required for the built-in server.

## Reproduce the configuration

Prerequisites: the existing Lightspeed Azure/Entra configuration, an initialized DevWorkspace, the demo namespace, and authenticated `oc`, Ruby and Helm. The integration deliberately reuses the installed provider rather than storing a provider credential in values files.

From the repository root:

```bash
ruby vm-cloud-native-demo/prereqs/scripts/agentic.rb --check
ruby vm-cloud-native-demo/prereqs/scripts/agentic.rb --apply
```

`NAMESPACE` selects the demo namespace, `DEVSPACE_NAMESPACE` selects the presenter's workspace namespace, `DEVSPACE_NAME` selects the workspace, and `OLS_NAMESPACE` selects the existing Lightspeed namespace. The default workspace namespace is derived from `oc whoami`, as in the prerequisite installer. Service-account logins require an explicit `DEVSPACE_NAMESPACE`.

The top-level setup script runs this installer when `OLSConfig/cluster` exists (`ENABLE_AGENTIC_PREREQS=auto`). In auto mode it defers this optional step if the presenter workspace does not yet exist; initialize the workspace and run the installer afterwards. Set it to `true` to require the integration or `false` to skip it. No Git push is needed for this local setup step: it installs the chart from the checked-out files. Commit these files before relying on another checkout or Dev Spaces' clone.

The installer preserves the LLM provider and merges only `introspectionEnabled: true` and `toolsApprovalConfig: {approvalType: tool_annotations, approvalTimeout: 600}` into OLSConfig. Non-read tool calls remain subject to the documented Lightspeed approval mechanism.

Helm release `rocket-ramen-agentic-prereqs` in the Lightspeed namespace manages:

| Resource | Purpose |
| --- | --- |
| `rocket-ramen-agent-llm` Deployment, Service, ConfigMap and ServiceAccount | Internal OpenAI-compatible LiteLLM endpoint; uses the existing Azure Entra Secret and refreshes access tokens |
| `rocket-ramen-agent-llm-tls` Secret | Generated by the OpenShift service CA for HTTPS |
| `rocket-ramen-workspace-mcp` NetworkPolicy | Allows only the selected workspace identity from its namespace through the MCP service's existing ingress policy |
| `rocket-ramen-workspace-llm` NetworkPolicy | Restricts gateway ingress to the selected workspace; no public Route is created |
| `rocket-ramen-workspace-agent` Role and RoleBinding | Allows inspection and the relevant VM, build, PipelineRun, Deployment, Rollout, Service and Route operations in the demo namespace |
| `rocket-ramen-agent` workspace ConfigMap | OpenCode configuration, launcher and read-only connection checks |
| `rocket-ramen-agent-ca` workspace ConfigMap | Service CA bundle injected by OpenShift; TLS verification remains enabled |

The installer creates and retains `rocket-ramen-agent-llm-key` in the Lightspeed namespace and copies only this generated gateway key to a workspace Secret with the same name. Azure credentials stay in the Lightspeed namespace. Secrets are sent through process stdin and are not put in Helm values, command arguments, local files, or `last-applied-configuration` annotations. The gateway uses the documented database-free LiteLLM mode: its key is a shared gateway master key, it has no UI or per-user budgets, and Azure's upstream limits still apply. This is an independently configured community component, not part of the Red Hat Lightspeed support boundary.

Workspace resources use Red Hat's [ConfigMap automount mechanism](https://docs.redhat.com/en/documentation/red_hat_openshift_dev_spaces/3.29/develop-proc_mounting_configmaps) and [workspace-specific/deferred mounting annotations](https://docs.redhat.com/en/documentation/red_hat_openshift_dev_spaces/3.28/html/3.28.0_release_notes_and_known_issues/new-features). They target only `rocket-ramen` and take effect at the next start, avoiding an unexpected restart when setup is rerun. Start or restart the workspace through Dev Spaces after installation.

## Use and verify in Dev Spaces

Open **Terminal: Create New Terminal (Select a Container)** and select `node`:

```bash
cd /projects/rh-demos/vm-cloud-native-demo
bash /etc/rocket-ramen-agent/agent.sh --check
bash /etc/rocket-ramen-agent/agent.sh
```

The launcher pins OpenCode 1.19.5 using npm, sets the service CA and mounted configuration, and disables conversation sharing. Its first run needs access to the npm registry. The Kubernetes MCP connection uses the workspace's projected service-account token, not the presenter's cluster-admin token. Start a new agent process if a long-running session outlives its loaded token. File reads are allowed; edits, shell commands and MCP tools require approval. The client approval policy is separate from Lightspeed's console approval policy.

Workspace model requests go through the internal gateway directly to Azure, so they do not inherit the Lightspeed Service's prompt filters or tool-result inspection. MCP resource restrictions, Kubernetes RBAC and the workspace client's own approvals still apply. The console continues using the existing Lightspeed Service and its configured controls.

The connection check verifies TLS, MCP authentication, tool discovery, live demo VM inspection, and an LLM function-call response. It does not change cluster resources. The existing console backend was separately tested with a read-only question through `/v1/query`.

Offline checks from the repository root:

```bash
ruby vm-cloud-native-demo/prereqs/agentic/test_chart.rb
ruby -c vm-cloud-native-demo/prereqs/scripts/agentic.rb
```

The chart tests check the namespace boundary, absence of Secret/RBAC/delete/exec permissions, network peer selectors, credential file references and workspace-specific mounts. Live verification confirmed 30 MCP tools available to the scoped workspace identity, successful inspection of the demo VMs, and a tool-call response from the existing Azure deployment. OpenCode itself reported version 1.19.5, connected to the MCP server with `mcp list`, and returned `READY` through the configured model in a no-tool headless test. The workspace identity was also checked to deny demo Secret reads, cluster-wide RBAC writes, and pod reads in the Lightspeed namespace.

The workspace Role has no Secret or RBAC rules, no pod-exec permission, no deletion permission, and no cluster-wide binding. It can change workloads within the demo namespace, so it is an operator identity for that namespace, not a security sandbox for untrusted code. The shipped MCP server's resource restrictions are an additional boundary. Bootc migration/reset still run in the local presenter terminal with the original private setup files and SSH key.

Primary integration references: [Red Hat OpenShift MCP installation and RBAC](https://docs.redhat.com/en/documentation/openshift_container_platform/4.22/html/ai_applications/mcp-server), [Red Hat private coding assistant quickstart](https://docs.redhat.com/en/learn/ai-quickstarts/rh-private-coding-assistant), [LiteLLM Azure Entra refresh](https://docs.litellm.ai/docs/providers/azure), [LiteLLM database-free deployment](https://docs.litellm.ai/docs/proxy/docker_quick_start), and [OpenCode MCP configuration](https://opencode.ai/docs/mcp-servers/). The OpenCode configuration is checked against the pinned release, not assumed to match future documentation versions.

## Possible agent-assisted presentation flow

1. **Console, inherited application:** ask Lightspeed to inspect the `rocket-ramen` VMs, Services and latest bootstrap PipelineRun. Have it explain the actual running architecture using MCP evidence. Continue placing the demonstration order through the application as before.
2. **Dev Spaces, application modernization:** ask the workspace agent to explain the two Containerfiles and propose the existing frontend text and API header edits. Review the diff, then run the same existing build/deploy segment in the `openshift-cli` terminal. Have the agent inspect the resulting PipelineRun through MCP. The node-based agent has npm and source access; the separate `openshift-cli` container has `oc`. Keep the saved source and build artifact path unchanged.
3. **Console, coexistence and traffic:** ask Lightspeed to show current Route weights and API Service selection before each transition. Review its proposed change against the existing 50%/100% traffic steps and approve only the intended operation. The existing scripts remain available for deterministic execution and rollback.
4. **Local terminal, database migration:** run the existing bootc migration and retirement commands. Use Lightspeed to inspect VM and Service state afterwards and explain what moved; verify order preservation in the application. Do not replace the snapshot/data checks with an LLM's interpretation.
5. **Recap and reset:** ask for a live summary of the final container/container/VM placement. Run the existing data-preserving reset locally and use MCP to inspect the restored state.

These are changes to how the presenter inspects, requests and reviews the same operations. They do not add a new migration, change data-handling steps, or turn the demo into an unattended agent run.
